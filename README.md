# Crystallium — деплой и монетизация

Всё, что нужно для заливки на сервер и подключения рекламы/платежей.

## Что уже готово, а что нужно сделать вам

**Готово (код написан и проверен):** сама игра, сервер проверки платежей,
панель статистики, логика TON/Stars/аналитики.

**Нужно сделать вам, иначе ничего не запустится:**
- [ ] Создать `.env` из `.env.example` и заполнить реальными значениями
      (`.env` намеренно не включён в архив — там ваши секретные токены,
      их не может быть в шаблоне от меня)
- [ ] Создать бота через @BotFather (если ещё нет) и подключить к нему
      Mini App — см. Шаг 2.5
- [ ] Арендовать/настроить хостинг с HTTPS и залить туда файлы
- [ ] Получить AdsGram blockId, настроить Stars-инвойс — см. шаги 3 и 6

Дальше — подробно, по шагам.

## Структура архива

```
deploy/
├── public/
│   ├── index.html              ← сама игра
│   ├── config.js                ← ЕДИНСТВЕННЫЙ файл с настройками монетизации
│   ├── tonconnect-manifest.json ← манифест для подключения TON-кошельков
│   └── stats.html               ← панель статистики (для вас, не для игроков)
├── server.js                    ← backend (проверка платежей, приём аналитики)
├── package.json
├── .env.example                 ← скопировать в .env и заполнить
└── README.md                    ← этот файл
```

`index.html` больше не хранит настройки в localStorage и не даёт их редактировать
из игры — в настройках игрока остались только язык, звук, вибрация, кошелёк
и сброс прогресса. Все продакшен-настройки теперь в одном месте — `config.js`.

## Шаг 1. Хостинг фронтенда (index.html, config.js, манифест)

Подойдёт любой статический хостинг с HTTPS: Vercel, Netlify, Cloudflare Pages,
обычный VPS с nginx. Telegram Mini Apps **обязательно** требуют HTTPS.

Если у вас VPS — просто положите содержимое `public/` в корень сайта
(например `/var/www/crystallium`) и настройте nginx:

```nginx
server {
  listen 443 ssl;
  server_name ваш-домен;
  root /var/www/crystallium;
  index index.html;

  location /api/ {
    proxy_pass http://127.0.0.1:3000;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
  }
}
```

HTTPS-сертификат — через certbot: `certbot --nginx -d ваш-домен`.

## Шаг 2. Backend (server.js)

```bash
cd deploy
npm install
cp .env.example .env
nano .env        # заполнить значения (см. ниже)
node server.js   # проверить, что запускается
```

Для продакшена — через pm2, чтобы сервер перезапускался сам:

```bash
npm install -g pm2
pm2 start server.js --name crystallium
pm2 save
pm2 startup     # добавит автозапуск при перезагрузке сервера
```

### Обязательные переменные в `.env`

| Переменная | Что это | Где взять |
|---|---|---|
| `BOT_TOKEN` | Токен бота | [@BotFather](https://t.me/BotFather) → `/newbot` или `/token` |
| `TON_ADDR` | Ваш TON-кошелёк | уже вписан ваш адрес по умолчанию |
| `ADMIN_TOKEN` | Пароль для статистики | придумайте случайную строку (пароль-менеджер) |
| `WEBHOOK_SECRET` | Секрет вебхука Stars | придумайте случайную строку |
| `ALLOWED_ORIGIN` | Домен игры | `https://ваш-домен` |

`TONAPI_KEY` не обязателен для старта, но без него у tonapi.io более жёсткие
лимиты запросов — если игроков будет много, оформите бесплатный ключ на
[tonconsole.com](https://tonconsole.com).

## Шаг 2.5. Подключение игры к боту (Mini App)

Без этого шага игра будет просто сайтом — Telegram не будет знать, что это
Mini App, и `Telegram.WebApp` в коде не инициализируется (initData не придёт,
проверка платежей не будет работать).

1. Напишите [@BotFather](https://t.me/BotFather) → `/newapp` (если бота ещё
   нет — сначала `/newbot`).
2. Укажите ссылку на игру: `https://ваш-домен/index.html` (или просто
   `https://ваш-домен`, если index.html — корень сайта).
3. Дальше `/mybots` → выберите бота → **Bot Settings → Menu Button** →
   укажите ту же ссылку — тогда у пользователей в чате с ботом появится
   кнопка запуска игры.
4. Проверка: откройте бота в Telegram (не в браузере!) и нажмите кнопку
   меню — игра должна открыться внутри Telegram, а в настройках игры
   имя профиля должно быть вашим Telegram-именем, а не «Гость».
   Если показывает «Гость» — значит открыли не через Telegram, initData
   не пришёл, и платежи/проверки работать не будут.

## Шаг 3. AdsGram (реклама)

1. Откройте [adsgram.ai](https://adsgram.ai) → **Sign in through Telegram**.
2. **Add app** → укажите вашего Telegram-бота / ссылку на Mini App.
3. Создайте **Ad unit** типа **Reward** (вознаграждаемая реклама — именно
   она используется в игре за бустеры/энергию/доп-ходы).
4. Скопируйте **blockId** (вид `int-12345`).
5. Впишите его в `public/config.js`:
   ```js
   ADSGRAM_BLOCK_ID: "int-12345",
   ADSGRAM_DEBUG: false,
   ```
6. Залейте обновлённый `config.js` на сервер — game.html трогать не надо.

Пока `ADSGRAM_BLOCK_ID` пустой, игра показывает честный демо-ролик вместо
рекламы — это нормально для тестирования всего остального функционала.

## Шаг 4. TonConnect (подключение кошельков)

1. Убедитесь, что `public/tonconnect-manifest.json` доступен по адресу
   `https://ваш-домен/tonconnect-manifest.json` (откройте в браузере, должен
   отдаться JSON, а не 404).
2. Впишите реальный домен внутрь самого манифеста (`url`, `iconUrl` и т.д.).
3. В `config.js` укажите:

Без этого шага кнопка «Привязать кошелёк» будет молча падать с ошибкой —
кошельки не подключаются к манифесту без HTTPS и без совпадения домена.

## Шаг 5. Проверка TON-платежей (как это работает)

Раньше у всех игроков был **один и тот же** комментарий к переводу
(`CRYSTALLIUM-NOADS`) — сервер не смог бы понять, кто именно заплатил.
Это исправлено: теперь комментарий уникален для каждого игрока
(`CRYS-tg<его_telegram_id>`), и сервер сам ищет в блокчейне перевод с этим
комментарием на ваш адрес — по кнопке «Я оплатил — активировать».

Логика в `server.js` → `findTonPayment()`: опрашивает `tonapi.io`, смотрит
последние 100 событий вашего кошелька, ищет `TonTransfer` с нужным
комментарием и суммой ≥ `TON_MIN_NANO`. Ничего дополнительно настраивать не
нужно — просто держите `.env` заполненным.

### ⚠️ USDT (jetton) — важно

Кнопка выбора USDT в интерфейсе **по умолчанию скрыта**
(`ENABLE_USDT: false` в `config.js`). Проверка jetton-переводов устроена
сложнее, чем обычных TON-переводов (нужно вычислять адрес jetton-кошелька
отправителя и т.д.) и в `server.js` **не реализована**. Не включайте эту
кнопку, пока не допишете верификацию — иначе игроки будут платить, а сервер
не сможет это подтвердить. Если нужно — могу отдельно доделать.

## Шаг 6. Telegram Stars

1. Создайте инвойс через Bot API (один раз, с телефона/сервера с curl):
   ```bash
   curl -X POST "https://api.telegram.org/bot$BOT_TOKEN/createInvoiceLink" \
     -H "Content-Type: application/json" \
     -d '{
       "title": "Убрать рекламу навсегда",
       "description": "Crystallium — отключение рекламы",
       "payload": "remove_ads",
       "currency": "XTR",
       "prices": [{"label":"Без рекламы","amount":100}]
     }'
   ```
   В ответе будет `result` — это и есть ссылка/slug. Впишите в `config.js`:
   ```js
   STARS_INVOICE: "полученная_ссылка_или_slug",
   STARS_PRICE: 100,
   ```

2. Настройте вебхук бота на ваш сервер:
   ```bash
   curl -X POST "https://api.telegram.org/bot$BOT_TOKEN/setWebhook" \
     -H "Content-Type: application/json" \
     -d '{
       "url": "https://ваш-домен/api/telegram/webhook",
       "secret_token": "тот_же_WEBHOOK_SECRET_что_в_.env",
       "allowed_updates": ["message","pre_checkout_query"]
     }'
   ```

Дальше всё автоматически: игрок жмёт «Оплатить 100 ★» → Telegram присылает
`pre_checkout_query` → сервер подтверждает → после оплаты приходит
`successful_payment` → сервер помечает игрока оплаченным.

## Шаг 7. Когда всё проверено — включаем «только сервер»

Пока `PAY_API` в `config.js` пустой, кнопка «Я оплатил» в TON/USDT-режиме
активирует «без рекламы» **без проверки** (демо-режим для тестирования, чтобы
вы могли проверить остальной интерфейс без реального перевода денег).

Как только backend поднят и протестирован:
```js
PAY_API: "https://ваш-домен",
REQUIRE_SERVER_PAYMENT: true
```
После этого демо-активация полностью выключается — «без рекламы» включается
только после реального подтверждения сервером.

## Шаг 8. Аналитика

В `config.js`:
```js
ANALYTICS_ENDPOINT: "https://ваш-домен/api/events"
```
Игра сама начнёт слать события (старт/победа/поражение уровня, показы и
завершения рекламы, покупки, смена языка и т.д.) на ваш сервер батчами.
События также всегда сохраняются локально у игрока (для отладки на
устройстве), но именно эндпойнт даёт вам общую картину по всем игрокам.

## Шаг 9. Панель статистики

Откройте `https://ваш-домен/stats.html`, введите `ADMIN_TOKEN` из `.env`.
Увидите: уникальных игроков, DAU за 30 дней, самые сложные уровни (где чаще
всего проигрывают), досматриваемость рекламы, разбивку покупок по способу
оплаты, полный список событий.

**Обязательно задайте `ADMIN_TOKEN`** — без него `/api/stats` открыт всем.

## Шаг 10. Чтобы сервер не «засыпал» на Render

Бесплатный тариф Render усыпляет веб-сервис после **15 минут без запросов**,
а следующий запрос после сна будит его ~30–50 секунд.

Я добавил лёгкий эндпоинт для пинга:
```
GET /health   → просто отвечает "ok", ничего не считает и не пишет на диск
```

### Вариант A (рекомендую) — GitHub Actions

В архиве уже лежит готовый файл `.github/workflows/keepalive.yml` —
пингует `/health` каждые 10 минут сам, по расписанию, бесплатно.

Настройка:
1. Залейте весь проект (включая папку `.github/`) в свой репозиторий на
   GitHub — обычным `git push` или через веб-интерфейс (Add file →
   Upload files, не забудьте сохранить структуру папок).
2. В репозитории: **Settings → Secrets and variables → Actions →
   New repository secret** → имя `RENDER_URL`, значение — адрес вашего
   сервиса на Render, например `https://crystallium-abcd.onrender.com`
   (без `/health` на конце — он добавится сам).
3. Вкладка **Actions** в репозитории — workflow `keepalive` появится и
   начнёт тикать по расписанию. Можно сразу проверить вручную:
   Actions → keepalive → **Run workflow**.

Честно про нюансы GitHub Actions:
- Расписание (`cron`) в GitHub Actions **не гарантирует** точность —
  в моменты высокой нагрузки на GitHub задача может стартовать на
  несколько минут позже. Обычно это не критично (запас в 15-минутный
  тайм-аут Render есть), но 100% гарантии нет.
- Если репозиторий **приватный**, есть месячный лимит бесплатных минут
  (2000 мин/мес) — для пинга раз в 10 минут это расходуется с огромным
  запасом (пинг занимает секунды), беспокоиться не о чем. Если
  репозиторий **публичный** — Actions вообще бесплатны без лимита.
- Если в репозитории 60 дней не было ни одного коммита, GitHub сам
  отключает scheduled-задачи — раз в пару месяцев нужно что-то закоммитить
  (или просто нажать Run workflow вручную).

Как альтернатива/дублирование — можно параллельно завести ещё и
UptimeRobot (см. ниже), это не помешает, а только подстрахует.

### Вариант B — внешний сервис-пингер

- **[UptimeRobot](https://uptimerobot.com)** (бесплатно) — Add New Monitor →
  HTTP(s) → URL: `https://ваш-домен.onrender.com/health` → интервал 5 минут.
- **[cron-job.org](https://cron-job.org)** — то же самое, каждые 10 минут.

### Вариант C — «держать вкладку открытой у себя»

Я добавил в игру (`index.html`) необязательный «пульс»: пока вкладка с
игрой открыта **и видна** (не свёрнута и не в фоне), она сама раз в
8 минут стучится на `/health`. Работает автоматически, если `PAY_API` в
`config.js` заполнен — ничего доп. настраивать не нужно.

Но будьте честны с собой насчёт того, что это даёт:
- Это работает **только пока конкретно ваша вкладка открыта и активна**
  на экране. Свернули браузер, заблокировали телефон/комп, ушли спать —
  пинги прекращаются, и после 15 минут простоя сервис всё равно уснёт.
- Это **не решение для продакшена** — реальные игроки заходят не 24/7,
  ночью, когда никто не играет, сервер уснёт независимо от того, что вы
  там у себя открывали днём.
- Плюс: если у игры уже есть реальные игроки, каждый, у кого открыта
  вкладка, невольно тоже шлёт эти пинги — это скорее приятный бонус
  поверх варианта A, чем самостоятельное решение.

**Итог:** для честной постоянной работы — вариант A (GitHub Actions) как
основной. Вариант C — просто дополнительная подстраховка, не полагайтесь
на него как на единственный механизм.

### Про данные на бесплатном Render

Данные (`data/paid.json`, `data/events.jsonl`) на бесплатном тарифе **не
постоянны** — при пересборке/переразвёртывании диск может обнулиться. Для
реальных денег это риск: если файл с оплатами потеряется, придётся вручную
восстанавливать, кто платил. Подключите Render **Persistent Disk**
(платный, от $1/мес за 1GB) или перенесите `paid.json`/`events.jsonl` во
внешнюю БД.

**Самый надёжный вариант в целом** — платный план Render (Starter, от
~$7/мес): сервис не спит вообще, плюс постоянный диск. Для проекта с
реальными платежами это того стоит — просыпание на 30–50 секунд именно
в момент, когда игрок пытается заплатить, — плохой опыт и риск потерять
оплату.


## Чек-лист перед запуском

- [ ] `.env` заполнен (`BOT_TOKEN`, `TON_ADDR`, `ADMIN_TOKEN`, `WEBHOOK_SECRET`)
- [ ] `server.js` запущен и держится (pm2/systemd)
- [ ] `tonconnect-manifest.json` открывается по https и домен внутри совпадает
- [ ] `ADSGRAM_BLOCK_ID` вписан в `config.js`, `ADSGRAM_DEBUG: false`
- [ ] `STARS_INVOICE` создан, вебхук бота настроен
- [ ] Тестовый TON-платёж на 1.5 TON с правильным memo реально засчитался
      через кнопку «Я оплатил» (проверить на **testnet** или маленькой сумме)
- [ ] `stats.html` открывается только с правильным токеном
- [ ] `REQUIRE_SERVER_PAYMENT: true` выставлен **только после** проверки
      предыдущих пунктов
- [ ] Если хостите на Render (бесплатный тариф) — настроен внешний пинг
      `/health` каждые 5–10 минут (см. Шаг 10)

## Что не реализовано (честно, чтобы не было сюрпризов)

- Проверка USDT/jetton-платежей — только TON.
- Своя БД — сейчас JSON-файлы (`data/paid.json`, `data/events.jsonl`).
  Нормально для старта и первых тысяч игроков; при росте — перенесите
  `readPaid/markPaid/appendEvents` в Postgres/SQLite, остальной код трогать
  не придётся.
- Возвраты/чарджбэки Stars (`refunded_payment`) сервер не обрабатывает —
  добавить по необходимости в `/api/telegram/webhook`.
